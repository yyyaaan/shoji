# AGENTS.md — Shoji

Shoji is a native macOS app that organizes terminal sessions ("threads") into a
Liquid Glass card shelf and a Hub view. Two groups of threads:

- **Agents** — interactive coding-agent CLIs (`claude`, `codex`) running in a folder.
- **Tasks** — long-running commands (`docker compose up`, `pnpm dev`, watchers).

Mascot: **Hachi**, an Akita who appears on a card when that thread needs the user.

Shoji is NOT an editor, diff viewer or file browser (the user keeps Zed/VS Code for
those), and NOT an agent client: it never talks to models or APIs. It only hosts
terminals and watches their status.

**`PLAN.md` is the living state file.** Read its Status and Gotchas sections before
starting work. Update Status and tick milestone checkboxes when you finish a session.

## Stack

- Swift 6 + SwiftUI, deployment target **macOS 26** (Liquid Glass: `.glassEffect()`,
  `GlassEffectContainer`; AppKit `NSGlassEffectView` where SwiftUI falls short).
- Terminal core: **libghostty** (`GhosttyKit.xcframework`), built from a pinned Ghostty
  commit by `scripts/build-ghostty.sh`. Reads the user's `~/.config/ghostty/config`.
- Project file generated by **XcodeGen** from `project.yml`. Never hand-edit
  `.pbxproj`; edit `project.yml` and regenerate.
- No third-party Swift packages without asking first.

## Layout

```
project.yml                 XcodeGen spec (source of truth for targets/settings)
scripts/
  ghostty.version           pinned Ghostty commit + required Zig version
  build-ghostty.sh          builds Vendor/GhosttyKit.xcframework
  shoji-hook                tiny hook client: env + stdin JSON -> Shoji socket
Vendor/                     built xcframework (gitignored)
Sources/Shoji/
  App/                      app entry, window, commands/shortcuts
  Threads/                  Thread model, ThreadStore, JSON persistence
  Terminal/                 GhosttyBridge + SurfaceView (only place importing GhosttyKit)
  Status/                   socket listener, StatusEvent, hook/notify setup
  UI/Shelf/                 card shelf (Agents | Tasks), context menu, drag reorder
  UI/Panes/                 pane layouts (1 / 2 / 4), pane header, min/max
  UI/Hub/                   Hub view big cards
  UI/Hachi/                 mascot assets + needs-you presentation
Tests/ShojiTests/
docs/design/                design reference as standalone HTML (open in a browser)
```

## Commands

```
scripts/build-ghostty.sh                     # once, and after bumping ghostty.version
xcodegen generate                            # after any project.yml change
xcodebuild -scheme Shoji -configuration Debug build
xcodebuild -scheme Shoji test
```

If a command here is wrong or missing, fix this file in the same change.

## Hard invariants (do not break without the user's explicit OK)

1. **Ghostty is pinned.** Only `scripts/ghostty.version` decides the commit. Never
   upgrade as a side effect; a bump is its own change with notes in PLAN.md.
2. **Only `Terminal/` imports GhosttyKit.** Everything else talks to `GhosttyBridge`
   / `SurfaceView`. The embedding API is unstable; keep the blast radius small.
3. **Glass on chrome only.** Shelf, card frames, pane headers, Hub cards, toasts and
   menus are glass. Terminal content is always drawn on a solid background.
4. **No tmux or any multiplexer.** Persistence = relaunch with the CLI's own resume
   (`claude --resume <id>`, `codex resume <id>`) using the thread's stored resume id.
5. **One status path.** Every status change is a `StatusEvent` (from the socket or
   from libghostty callbacks: title, bell, notification, child exit) applied by
   `ThreadStore` on the main actor. UI never derives status by scraping output.
6. **Never type into a terminal on the user's behalf** except through an explicit user
   action (e.g. Hub "Allow once"), sending exactly the keystroke the UI shows. Log it.
7. **Hooks must never slow or break the CLIs.** `shoji-hook` exits 0 within ~100 ms
   and silently when Shoji isn't running.
8. **Don't touch the user's global CLI config** (`~/.claude`, `~/.codex`) without an
   explicit opt-in. Prefer per-launch injection (env vars, a settings file or config
   override passed at launch). Verify the current CLI flags before relying on them.
9. **Thread file is versioned.** `threads.json` has a `schemaVersion`; add a migration
   whenever the shape changes. Never silently drop a user's threads.

## Conventions

- Swift 6 strict concurrency. `ThreadStore` is `@MainActor @Observable`.
- Child processes get `SHOJI_THREAD_ID` and `SHOJI_SOCKET` in their environment so
  hooks can report which thread they belong to.
- Status is never color-only: every state has its own icon shape plus a text label.
- Every view gets a SwiftUI preview backed by mock threads (`Threads/Mock.swift`).
- Keep changes small and milestone-scoped; one milestone item per PR when practical.

## Design reference

Chosen direction: **Option B — card shelf + split panes**, plus the **Hub view**.
The source of truth is the HTML in `docs/design/` (`threads-shelf.html`, `hub.html`):
read it for layout, spacing, radii and colors, and open it in a browser to see it.
It's a web mockup, so translate it to SwiftUI; don't port the HTML/CSS literally.
Status palette (dark UI):

| State | Color | Icon |
|---|---|---|
| Working | `#74B8FF` | spinning arc |
| Needs you | `#FF9F43` | ring + "!", card glow, count badge, Hachi |
| Done | `#E2E8F0` | check |
| Idle | `#E2E8F0` at 55% | dashed ring |
| Task running | `#4FD1B5` | pulsing dot |
| Exited / error | `#FF8787` | ring + × |

Terminal background `#0C0F15`. UI type: system font (SF Pro); terminal font comes
from the Ghostty config.

## Don't

- Don't add an editor, diff view, file tree or git UI.
- Don't call model APIs or embed agent SDKs; Shoji only hosts the CLIs.
- Don't put glass, blur or transparency behind terminal text.
- Don't parse terminal output for status (invariant 5).
- Don't hand-edit `.pbxproj` or commit `Vendor/`.
- Don't change an invariant above without asking; propose it in PLAN.md Open questions.
