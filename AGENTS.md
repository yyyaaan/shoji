# AGENTS.md — Shoji

Shoji is a native macOS app that organizes terminal sessions ("threads") into a
Liquid Glass card shelf and a Hub view. Every thread is the user's own shell: they `cd`
anywhere and run coding-agent CLIs (`claude`, `codex`) or long-running commands
(`docker compose up`, `pnpm dev`, watchers) in it, and quit back to the prompt as usual.
Shoji shows what's running and what needs the user.

Mascot: **Hachi**, an Akita who appears on a card, and in the window's top-left corner, when a thread needs the user.

Words used everywhere (code, docs, chat): a **thread** is one hosted shell session, whatever runs in it; the **shelf** is the strip of **cards** across the top, one card per thread in the user's order, with **bars** splitting it into groups that mean whatever the user wants (no titles); a **pane** shows an open thread's terminal below the shelf; the **Hub** (planned) shows big cards.

Shoji is NOT an editor, diff viewer or file browser (the user keeps Zed/VS Code for
those), and NOT an agent client: it never talks to models or APIs. It only hosts
terminals and watches their status.

**`PLAN.md` is the living state file.** Read its Status and Gotchas sections before
starting work, then check `docs/handoffs/` for work addressed to you. Update Status and
its task list (Now / Next / Later / Parked / Done) when you finish a session.

## Stack

- Swift 6 + SwiftUI, deployment target **macOS 26** (Liquid Glass: `.glassEffect()`,
  `GlassEffectContainer`; AppKit `NSGlassEffectView` where SwiftUI falls short).
- Terminal core: **SwiftTerm** (MIT, Swift package), pinned to an exact version in
  `project.yml`. Use its Metal renderer. Themes and fonts are Shoji settings.
- Project file generated by **XcodeGen** from `project.yml`. Never hand-edit
  `.pbxproj`; edit `project.yml` and regenerate.
- No third-party Swift packages besides SwiftTerm without asking first.

## Commands

```
xcodegen generate        # after any project.yml change and on a fresh clone (.xcodeproj is not committed)
xcodebuild -scheme Shoji -derivedDataPath build -destination 'platform=macOS' -skipPackagePluginValidation build
xcodebuild -scheme Shoji -derivedDataPath build -destination 'platform=macOS' -skipPackagePluginValidation test
open build/Build/Products/Debug/Shoji.app
scripts/package.sh [version]     # universal Release app + DMG, ad-hoc signed
# Releasing: bump MARKETING_VERSION in project.yml in a PR; merging it publishes vX.Y.Z (release.yml)
```

`-skipPackagePluginValidation` is needed because SwiftTerm runs a build-tool plugin; in Xcode, click Trust & Enable once instead.

`main` is protected: work on a branch, one PR per change, green `test` check, squash merge. Debug builds are their own app to macOS (bundle id `fi.yan.shoji.debug`, shown as Shoji Debug, with their own notifications and UserDefaults) and keep their threads and hook socket in `~/Library/Application Support/Shoji-Debug`, apart from the installed app's `Shoji` folder, so a dev build can run next to it.

If a command here is wrong or missing, fix this file in the same change.

## Hard invariants (do not break without the user's explicit OK)

1. **SwiftTerm is pinned** to an exact version in `project.yml`. Never upgrade as a
   side effect; a bump is its own change, re-running the terminal checklist in PLAN.md.
2. **Only `Terminal/` imports SwiftTerm.** Everything else talks to the
   `TerminalBackend` protocol, so the engine stays swappable (libghostty is the
   documented fallback).
3. **Glass on chrome only.** Shelf, card frames, pane headers, Hub cards, toasts and
   menus are glass. Terminal content is always drawn on a solid background.
4. **No tmux or any multiplexer.** Persistence = relaunch with the CLI's own resume
   (`claude --resume <id>`, `codex resume <id>`) using the thread's stored resume id.
5. **One status path.** Every status change is a `StatusEvent` (from the socket or
   from terminal delegate callbacks: title, bell, process exit, and the zsh
   integration's `OSC 1337 ; ShojiEvent=…` reports) applied by `ThreadStore` on the
   main actor. UI never derives status by scraping output.
6. **Never type into a terminal on the user's behalf** except through an explicit user
   action (e.g. Hub "Allow once"), sending exactly the keystroke the UI shows. Log it.
   Relaunching is not typing: the zsh integration runs `claude --resume <id>` or `codex resume <id>` at a
   restored shell's first prompt, and leaves any other last command at the prompt for
   the user to run with Return.
7. **Hooks must never slow or break the CLIs.** `shoji-hook` exits 0 within ~100 ms
   and silently when Shoji isn't running.
8. **Don't touch the user's global CLI config** (`~/.claude`, `~/.codex`) without an
   explicit opt-in. Prefer per-launch injection (env vars, a settings file or config
   override passed at launch). Verify the current CLI flags before relying on them.
9. **Thread file is versioned.** `threads.json` has a `schemaVersion`; bump it and add a
   migration when an older or newer Shoji couldn't read the new shape. Additive optional
   fields and removed fields that are simply ignored stay on the current version. Never
   silently drop a user's threads.

## Terminal setup rules (known SwiftTerm pitfalls with Claude Code)

- Launch every thread as the user's **login shell** (`$SHELL -l -i`) so PATH and
  environment match a normal terminal. A GUI app's own environment is not enough.
- **zsh integration** (`scripts/shoji.zsh`): Shoji sets `ZDOTDIR` to a `.zshenv` that
  restores the user's and sources it, so their dotfiles load unchanged. On the first
  prompt it adds precmd/preexec hooks and `claude` / `codex` functions that pass Shoji's
  hooks (`--settings`, `-c hooks={…}`). Other shells run without it (no folder, command or agent status).
- Set a **large scrollback** (default is only 500 lines; long agent replies overflow it).
- **Shift+Enter** must insert a newline in Claude Code: if the CLI doesn't receive a
  distinct key, the view sends ESC + CR for Shift+Enter.
- Offer **Option as Meta** (on by default) so Option shortcuts reach the CLIs.
- For link handling, install a **proxy `TerminalViewDelegate`** that forwards every
  call; don't rely on subclass overrides of delegate defaults.
- Claude Code only emits its own desktop notifications in a few terminals; Shoji's
  "needs you" status comes from hooks via the socket, never from those notifications.

## Conventions

- Swift 6 strict concurrency, no default actor isolation. `ThreadStore` and `TerminalSessions` are `@MainActor @Observable`.
- The thread model is `ShojiThread`; `Thread` would shadow `Foundation.Thread`.
- Tests use Swift Testing. The test host runs the app headless (no shells, no socket); keep `ShojiApp.isHeadless` in sync if launch wiring changes. Suites follow features (Activity, Shelf, Panes, Navigation, PaneLayout, StatusEvent, ThreadFile, ThreadLaunch); `Support.swift` has `store.send(_:to:)` and `numberedThreads(_:)`. Extend a scenario before adding a near-duplicate test.
- To check UI by hand, launch the built app and use `screencapture -l <windowid>`. Press controls with System Events `perform action "AXPress"`; never send keystrokes, because macOS keeps the user's frontmost app and keystrokes go there.
- **Zoom:** chrome metrics (font sizes, card and header sizes, radii, paddings) multiply by `@Environment(\.zoom)`, so ⌘+ / ⌘− scale the UI with the terminal text. New chrome must do the same.
- **Shortcuts:** add new ones to the `Shortcut` catalog in `App/Shortcuts.swift`; the menu bar and the ⌘/ sheet both read it. ⌘K opens the quick terminal (it means "clear" in other Mac terminals; Shoji chose this on purpose).
- Child processes get `SHOJI_THREAD_ID` and `SHOJI_SOCKET` in their environment so
  hooks can report which thread they belong to. The zsh integration also reads
  `SHOJI_ZSH`, `SHOJI_USER_ZDOTDIR`, `SHOJI_CLAUDE_SETTINGS`, `SHOJI_CODEX_HOOKS`, `SHOJI_RESUME` and
  `SHOJI_PREFILL`; inherited `SHOJI_*` variables are stripped first.
- Status is never color-only: every state has its own icon shape plus a text label.
- Every view gets a SwiftUI preview backed by mock threads (`Threads/Mock.swift`).
- Keep changes small; one task per PR when practical.

## Handoffs between agents

Several agents work on Shoji in parallel (for example app code and design). They pass work to each other through files in `docs/handoffs/`, not only in chat.

- **One file per handoff:** `docs/handoffs/<yyyy-mm-dd>-<from>-to-<to>-<topic>.md`, e.g. `2026-10-28-design-to-app-hachi.md`. Roles are short names: `app`, `design`, `review`, or `any`.
- **Keep it short:** what is wanted and why, links to the files, assets and decisions it relies on (link long specs, don't copy them), a checklist of asks, and how to tell it is done. Questions for the user go to PLAN.md Open questions, not here.
- **At session start,** read `docs/handoffs/` along with PLAN.md. Take files addressed to your role or `any`, and add `Taken by: <role>, <date>` at the top so two agents don't do the same work.
- **When done,** delete the handoff file in the same change as the work. If only part is done, remove the finished asks and leave the rest. Move anything lasting to its real home first: decisions, gotchas and follow-up tasks to PLAN.md, rules to AGENTS.md, specs to `docs/design/`. Git history keeps the record.
- **Don't edit someone else's open handoff** beyond claiming it or removing asks you finished.
- **Handoffs stay out of git** (only `docs/handoffs/README.md` is tracked), because every agent shares this one checkout. If agents ever work in separate worktrees, branches or machines, commit them instead, or they won't see each other's handoffs.

## Design reference

Chosen direction: **Option B — card shelf + split panes**, plus the **Hub view**.
The source of truth is the HTML in `docs/design/` (`threads-shelf.html`, `hub.html`):
read it for layout, spacing, radii and colors, and open it in a browser to see it.
It's a web mockup, so translate it to SwiftUI; don't port the HTML/CSS literally.
Status palette (dark UI):

| State | Color | Icon |
|---|---|---|
| Working | `#74B8FF` | spinning arc |
| Needs you | `#FF9F43` | ring + "!", card glow, count badge, Hachi |
| Done | `#E2E8F0` | check |
| Idle | `#E2E8F0` at 55% | Torii gate (`docs/design/status/`) |
| Task running | `#4FD1B5` | pulsing dot |
| Exited / error | `#FF8787` | ring + × |

Terminal background `#0C0F15`. UI type: system font (SF Pro); terminal font and theme
come from Shoji's settings (default: a monospaced system font and a dark theme).

## Don't

- Don't add an editor, diff view, file tree or git UI.
- Don't call model APIs or embed agent SDKs; Shoji only hosts the CLIs.
- Don't put glass, blur or transparency behind terminal text.
- Don't parse terminal output for status (invariant 5).
- Don't hand-edit `.pbxproj`.
- Don't change an invariant above without asking; propose it in PLAN.md Open questions.
